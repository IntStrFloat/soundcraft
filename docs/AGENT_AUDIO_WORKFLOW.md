# Работа агента со звуком в SoundCraft

Читай этот файл в начале каждой сессии вместе с корневым `AGENTS.md`. Для задачи по звуку
самостоятельно обеспечь работающий backend, выполни обработку и проверь результат. Обычный
запуск, сборка при отсутствии бинарника и обратимые правки входят в выполнение задачи.

## Запуск и сохранение состояния

1. Используй уже подключённый MCP `soundcraft`. Сначала вызови `inspect_session` и проверь
   нужные дорожки, клипы и сохранённый путь. Для существующего материала выполни через
   `execute` команду `session.audio_health` и разберись с отсутствующими источниками.
2. Если инструменты MCP недоступны в текущем клиенте, найди установленный CLI: путь из
   `codex mcp get soundcraft --json`, затем `soundcraft-cli` в `PATH`, затем
   `target/release/soundcraft-cli` этого checkout (`.exe` на Windows). Локальная установка
   также может находиться в каталоге пользователя `.codex/mcp/soundcraft/`.
3. Если бинарника нет, один раз собери его из корня репозитория:

   ```sh
   cargo build --release -p soundcraft-cli
   ```

   `rust-toolchain.toml` фиксирует Rust **1.95.0**. Проверь найденный бинарник через
   `--version` и наличие `sound.design` через `describe sound.design`, прежде чем применять
   команды этого форка к старой установленной версии.
4. Продолжай работу через CLI `run`/`script` или собственный постоянный stdio-клиент MCP.
   Пустой `mcp` — сервер, ожидающий запросы; не запускай его как обычную завершающуюся
   shell-команду. В stdio используй **UTF-8** для stdin/stdout и JSON-RPC строку на запрос:
   `initialize` с версией `2025-06-18`, затем `tools/call`. Читай ответ после каждого вызова,
   проверяй `isError`; диагностический stderr храни отдельно от JSON stdout.
5. Один процесс MCP хранит одну сессию. Отдельные `CLI run`/`script` начинают новую:
   объединяй правки в один скрипт либо продолжай с `--in project.scraft`. Сохраняй сессию
   и аудио явными путями; завершение процесса без сохранения теряет несохранённые правки.

Для ограниченного task-scoped сервера укажи существующие каталоги отдельно:

```sh
soundcraft-cli mcp --automation-read-root /absolute/media --automation-write-root /absolute/output
```

Повтори read-root для отдельной SFX-библиотеки, если она нужна. Используй абсолютные пути
в вызовах. Исправляй конкретный отсутствующий корень, сохраняя назначение read/write.

GUI нужен для визуального контроля, работы в открытом проекте или по запросу пользователя.
Переиспользуй уже работающий экземпляр и его фактический control-порт. Если нужен новый
экземпляр, запусти `cargo run --release -p soundcraft -- --control 0`, прочитай выведенный
`SOUNDCRAFT_CONTROL_PORT` и подключись через `soundcraft-cli mcp --connect PORT`.
Не запускай второй экземпляр для того же проекта. `--connect` работает с сессией GUI;
headless MCP хранит собственную сессию. Корни автоматизации нельзя совмещать с `--connect`.

## Выбор из SFX-библиотеки

Найди библиотеку в таком порядке: существующий путь `SOUNDCRAFT_SFX_ROOT` из окружения;
`../../SFX` относительно корня этого checkout; `SFX` внутри checkout. В текущей раскладке
рабочая библиотека находится рядом с папками `work/`, `sources/` и `analysis/`, вне форка.

Прочитай её `README.md`, таксономию и каталог/манифест, если они присутствуют. Сначала
подбирай **применение в монтаже**: появление/убирание текста, появление изображения,
движение, переход, ударный акцент и другие подтверждённые категории. Затем выбирай вайб
из общей таксономии. Названия и смысл вайбов должны совпадать во всех категориях;
не создавай локальные синонимы и не заполняй пустую категорию случайным звуком ради количества.

Основные файлы каталога: `taxonomy.json`, `manifest.json` и `catalog.csv`. Вайб библиотеки —
метка подбора, а не значение enum MCP: «резкий», «тревожный» и «грустный» не передавай
буквально в `design_sound.vibe`. Для готового SFX сначала импортируй сам файл; характер
уточняй обработкой. Встроенные восемь пресетов остаются стартовыми рецептами.

Проверяй запись каталога: источник/автор, библиотека, лицензия и допустимое использование,
связанный таймкод видео, происхождение аудио и сведения об обработке. Отрывок обучающего
видео с речью/музыкой остаётся референсом. Оригинал из библиотеки, извлечённый пример,
обработанная версия и самостоятельно синтезированный аналог должны различаться в метаданных.
Не выдавай предположительное совпадение за установленный источник.

Сначала прослушай подходящие кандидаты, оцени атаку, хвост, шум/речь, выразительность и
место под реплику/музыку в монтаже. Популярность названия не подтверждает качество конкретного
файла. Сохраняй чистые исходники; обработанные варианты создавай отдельно.

## Цикл: запрос → вариант → проверенный результат

1. Переведи запрос пользователя в применение, характер, длительность и точку синхронизации.
   Общий смысл языка интерпретирует модель клиента. `brief` на сервере использует небольшой
   RU/EN keyword fallback; при нюансах передавай явные `purpose` и `vibe`, читай assumptions.
2. Для подходящего библиотечного звука вызови `import_audio`, затем используй его `clip` id.
   `plan_sound` даёт стартовый рецепт; `design_sound` создаёт синтетический звук либо вариант
   `source_clip` на **новой дорожке**. Храни возвращённые id и фактическое уникальное имя.
3. Получи точные id, диапазоны, единицы и параметры через `list_plugins`. Добавляй цепочку
   через `apply_effect_chain`, уточняй `set_plugin_params`, сравнивай `bypass_plugin`.
   При `append` эффекты идут после последнего занятого слота; `replace` заменяет вставки.
   Старая автоматизация переиспользуемых insert-слотов очищается, volume/trim сохраняется.
4. Для огибающих используй `set_automation_point`, для offline-обработки `process_audio`.
   Остальные операции найди через `list_commands`/`describe`: `execute` и `batch` дают доступ
   ко всему редактору. Обычный `batch` может оставить выполненную часть при ошибке;
   `design_sound` и `apply_effect_chain` отменяются одним `undo`.
5. Вызови `preview_audio` для нужной дорожки/диапазона и оцени фактический WAV. Проверь
   `analyze_audio`: peak, true peak, RMS, clipping, тишину и предупреждения об источниках.
   Меняй звук и повторяй проверку. Если аудио не прослушано/не оценено, так и скажи;
   одни измерения не позволяют утверждать, что вариант хорошо звучит.
6. Экспортируй нужный диапазон через `bounce_mix` в WAV/AIFF/FLAC и сохрани редактируемый
   проект через `save_session`. Для отдельного клипа/стемов найди `file.export_clips` или
   `file.bounce_stems`: mix bounce включает все слышимые дорожки. Открой сохранённый проект
   повторно в проверочной сессии и убедись, что `missing` пуст и обработка сохранилась.

Предпросмотр/анализ ограничены 30 секундами; по умолчанию берётся до 10 секунд. Дай `start`
и `end` либо `duration`, включая хвост реверберации/задержки. Offline preview начинает с
чистого состояния эффектов без preroll и сам не удлиняет хвост. Headless preview возвращает
аудио клиенту, а не включает колонки. Короткому SFX часто не хватает 400 мс для LUFS;
`null` не заменяй вымышленным значением. Peak normalization не является LUFS-мастерингом.

## Перед завершением

Проверь читаемость экспортированного файла, реальную длительность/уровни, сохранность
оригинала и редактируемого проекта. Укажи пути результата, что прослушано и что проверено
только технически. Отдельно назови недоступные плагины, отсутствующие источники или
неустановленное происхождение материала, если это влияет на результат.

Публичный форк сохраняет правила `AGENTS.md`: bundled audio — только оригинальное,
CC0 или совместимо лицензированное открытое содержимое, с записью в `ATTRIBUTION.md`.
Внешняя рабочая SFX-библиотека не получает лицензию форка автоматически. Ссылки на источники
и локальная лицензия не означают разрешение публиковать чужие библиотеки в GitHub.

Подробности: [MCP](mcp.md), [sound design](sound-design-mcp.md),
[control protocol](control-protocol.md). Для изменений кода выполняй штатные проверки
репозитория; этот документ не заменяет его инженерные инструкции.
